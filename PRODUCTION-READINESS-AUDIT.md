# Usehlsvideoplayer 2.0 production readiness audit

This audit records an earlier candidate and its follow-up branch checks. Its digests and measurements do not identify the later upgrade. See the [upgrade verification report](docs/verification-report.md) for subsequent recovery, credential renewal, quality, and metrics work. The verdict and gate descriptions below reflect the audit date. See the [current release checks](docs/qualification.md).

**Verdict at the time of the audit: FAIL for release.** The local candidate fixes the reproduced high-impact request-policy and lifecycle defects. The full release criteria still require 6-hour and 24-hour evidence, Safari on macOS and iOS, Chrome on physical Android hardware, and verification of the hosted release controls. A successful local browser suite cannot close those gates.

Baseline: `cd9ffc58a72abd320be9d3407b7ce46e7788a393`, verified against `origin/master` before that audit began. That commit merged TypeScript 7.0.2. Findings refer to that baseline unless stated otherwise. Initial remediation was tested in the local working tree; later hosted branch results are identified separately below. The historical local source digest is `ce167d8ead67fdc3c4f9b62365fd79621745342f1bc2e7a5fa221f3f9681f379` (SHA-256 over 57 sorted repository paths and their content hashes, excluding this report and generated output).

## Architecture and ranked findings

The controller owns media attachment, commands, snapshots and recovery. The two adapters translate browser/hls.js APIs and expose engine features; hls.js owns playlist parsing, loading, ABR and buffering. React owns ref reconciliation and subscriptions. It does not drive the engine state machine. `/core` has no React import or runtime requirement; the npm tarball was installed in a consumer without React to exercise both module formats. The architecture remains intact.

No critical defect was reproduced. The remaining limitations below prevent a release recommendation. Core attachment and event handling still assume real browser element semantics, and an injected adapter is trusted to implement synchronous detach and cancellation. Loading and playback phases are exposed by the controller; the native element and hls.js still maintain their own internal states. The controller never treats a media event name alone as proof that an old session can publish into a replacement.

## Primary Attack Vectors

- **AV-1:** A hostile playlist redirects or points to an out-of-policy child playlist, key or segment. Credential exposure depends on the request reaching that server, including any preflight.
- **AV-2:** A late engine callback, play rejection or reentrant observer corrupts the active source, or teardown runs over a replacement engine. Repeated faults can also consume timers and network capacity.
- **AV-3:** A release maintainer supplies an unrelated, stale, skipped or incomplete run; an environment-free historical workflow obtains npm authority.
- **AV-4:** A trusted runtime integration enables upstream debug or a long-running encrypted stream rotates key URIs and retains records.

## Implicit Assumptions

- An allowed origin is trusted to receive the headers or cookies selected for it. Use a dedicated media origin; an origin allowlist cannot grant or revoke server permissions. Native HLS does not intercept segment requests and cannot enforce this policy or inject headers. Protected mode requires the hls.js FetchLoader and fails closed when it cannot be selected.
- Each browser realm owns its media element. Applications do not attach unrelated engines directly to an owned video or run arbitrary custom code in a supposedly isolated loader. Requests already delivered before a policy update cannot be recalled.
- Device drivers are provisioned for real hardware. Remote GitHub reviewers, tag rules and the npm trust environment are external configuration. A passing loopback H.264 fixture does not prove compatibility with a different codec, CDN or device.

The generated LL-HLS origin serves 500 ms CMAF partials with 2-second parents and advertises `CAN-BLOCK-RELOAD=YES`. The browser gate requires partial-media requests, a reload with `_HLS_msn` and `_HLS_part` held at least 250 ms, continuing decoded frames, and a seek back to the live edge. Chromium exercises 1.5 MB/s → 80 KB/s → 1.5 MB/s download profiles plus per-part delay; Firefox exercises delay changes. The suite also covers a timestamp discontinuity, a live DVR window, malformed playlists, HTTP 404 media, HTTP 503 recovery, HTTP 403 authentication expiry, alternate audio and a rendered WebVTT cue. It does not certify LL-HLS delta/rendition reports, caption codecs such as CEA-708, glass-to-glass latency or real CDN failover.

The separate [detailed browser evidence](test-results/browser-detailed) measured a 285 ms manual downshift, 1.71 s manual upshift and 6.43 s automatic downshift after reducing throughput to 65 KB/s. The measured LL-HLS case constructed the controller in 0.7 ms, returned from attachment in 47 ms and presented its first frame 2.31 s after the attachment call began. It recorded 15 successful part responses and four blocking reloads of 500–512 ms. These are individual observations. The Vite playback consumer weighed 751,336 bytes / 204,631 gzip including hls.js; selection only weighed 255 bytes / 212 gzip without hls.js or React.

The controller benchmark issues 100,000 `progress` events per measurement and distinguishes EventTarget-only overhead, unchanged snapshots and actual publications. The React selector rendered zero times for 11 independent updates; the full snapshot subscriber rendered 22 times in Strict Mode. A successful short heap comparison alone cannot establish retention behaviour; the soak probes multiple post-GC samples and keeps detached nodes, listeners, timers, requests, blob ownership, buffers and frames separate. The final one-minute candidate smoke passed. A [preliminary 30-minute run](test-results/soak/soak-repeated-live-playbac-9221e-wn-retain-bounded-resources/samples.ndjson) passed seven teardown cycles with zero active listeners, detached roots, media URLs, timers and requests after every teardown. It collected 33 active samples, a maximum 34-second buffer and a late-minus-warm post-GC heap median of +110,388 bytes with no increase in node or listener medians. This run preceded the final lifecycle adjustment and is not release evidence for the exact candidate. A superseded repeat was stopped rather than counted. An earlier immediate post-GC probe reported 160 nodes with zero active listeners, timers, requests and blob URLs; the harness now checks settling over a bounded 10-second window and keeps the intermediate samples.

## Verification and change map

- **Runtime:** `src/controller.ts`, `src/useHlsVideoPlayer.ts`, `src/engines.ts`, `src/core.ts` and `src/engine-selection.ts` implement ownership, stale callback protection, policy reconciliation, typed diagnostics and selection-only bundling.
- **Build and package:** `package.json`, `package-lock.json`, `tsconfig.playground.json`, `scripts/{build,compiler,typecheck,check-package}.mjs` select compatible current packages, verify strict declarations, install the real tarball, and exercise Vite tree shaking and Next.js.

- **Release controls:** `.github/{dependabot.yml,actionlint.yaml,workflows/*.yml}`, `scripts/{check-qualification,device-check}.mjs` and `test/release.test.mjs` configure and test the separate gates. `README.md`, `SECURITY.md` and `docs/` describe the actual contracts and limitations.
