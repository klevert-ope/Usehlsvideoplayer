## Implemented changes

The pre-existing controller, adapters, React hooks, security policy and packaging were extended rather than replaced.

- Failure-specific upstream loading/decoder recovery, bounded reconstruction fallback, progress-based completion, optional startup/stall deadlines, source cancellation and live-edge/DVR restoration.
- Abortable asynchronous header providers and one application-owned authentication refresh in flight per source. Renewed signed URLs cannot widen the allowlist; denied, failed, timed-out and stale refreshes are handled explicitly. Renewal consumes the existing source-wide budget.
- Optional automatic quality preferences, conservative ladder caps, lowest-rendition fallback, manual override and explicit precedence over conflicting upstream settings.
- Optional session/recovery/failure/quality/bandwidth/first-frame measurements, without new event discriminants, telemetry transport or runtime dependencies.
- Playground renewal/quality demonstrations, API/security/usage documentation, packed consumer lifecycle/declaration checks and an encrypted rotating-key soak workload.

All additions preserve legacy hook names, object-ref compatibility, existing root/core exports, module formats, synchronous header providers and adapters without recovery methods. New diagnostic fields remain optional in public declarations.

## Failures found and resolved during execution

- Four focused tests failed before controller implementation: in-place recovery, no-progress watchdogs, coalesced cancellation and renewal failure handling. They pass after implementation. These establish previously missing policies, not previously claimed Safari defects.
- The initial formatting check failed on `docs/troubleshooting.md`; it was corrected.
- Updating Playwright left its expected Chromium headless revision absent. That launch-only run failed without exercising playback. Subsequent tests used installed Chrome; the failed launch directory was retained.
- Adding a second quality-related label made an existing browser locator ambiguous. The full run exposed it; the preference label was made distinct and a playground regression added. The final Chrome run passed all 20 cases.
- An actual browser regression demonstrated an upstream minimum-bitrate floor defeating a startup-only preference: the first segment came from the high rendition. Resetting that floor when valid preferences are supplied makes the first segment come from the intended low rendition. Before/after evidence is in `test-results/upgrade-startup-floor-before` and `test-results/upgrade-startup-floor-after`; cap/manual/fallback tests also include conflicting upstream settings.
- The earlier standard soak was interrupted to apply that correction. It is not counted as an endurance pass; both final 30-minute workloads started after the runtime correction.
- Windows WebKit timed out navigating the playground in two attempts. A separate blank-page probe returned no native HLS capability. The native test now probes before navigation and explicitly skips unsupported engines; this does not establish physical Safari compatibility or resolve the Windows navigation issue.
- The last formatting sweep found the newly written report and a package-check line unformatted. They were formatted before final verification.

## Performance and resource evidence

The final measured runtime emits 63,904 bytes of ESM JavaScript, 13,474 bytes gzipped, excluding dependencies. The planning baseline was 46,229 / 10,263 bytes. A minified browser core including hls.js is 759,687 / 206,740 bytes versus 751,336 / 204,629 bytes at baseline: about 2.1 KB additional gzip. Selection-only bundling remains 255 bytes, without React or hls.js. These are implementation costs, not startup benchmarks.

The final Chrome loopback sample measured 1.400 s attachment-to-playing VOD startup, 0.328 s live startup and 0.365–0.535 s readiness across five source replacements. Both short samples had zero measured rebuffering. Post-GC heap changed by +1,136,564 bytes across the workload. The baseline used another browser build and host load; no performance improvement or leak-free claim follows from that comparison. See local benchmark JSON under `test-results/upgrade-release-candidate-chrome`.

Both final endurance workloads used the runtime fingerprint above. The standard run completed at 12:02:58 UTC and the encrypted run at 12:05:51 UTC on 17 November. Their Playwright result files report passed. Local `test-results/upgrade-evidence/soak-summary.json` records the aggregate evidence.

Each workload completed seven cycles with 33 active samples. The final teardown of each had zero pending requests, timers, event listeners, detached roots and owned MediaSource URLs, with 12 baseline DOM nodes. The standard workload's request-failure counter rose four times, each first observed immediately after destruction; this is consistent with cancellation of pending requests, not a measured terminal playback failure. Soak measurements cover renderer JavaScript heap, DOM/listeners, detached roots, timers, pending requests, MediaSource URLs, buffer lengths and frames. They exclude native decoder/worker memory and physical-device power. The application and upstream own their own allocations; a small heap delta alone cannot prove cleanup.

## Remaining risks and release recommendation

Release readiness: **BLOCKED** until the retained exact-candidate physical-device and long-soak gates pass. This is locally implemented and tested work, not a production-qualified release.

- Native HLS cannot enforce injected headers, per-request origins or reliable HTTP-status renewal. Its decoder recovery and stall behaviour still need real devices.
- Proactive credential rotation, server authorisation, cross-player refresh coordination, CORS/cookies and CDN trust remain application responsibilities. Reactive retries remain finite.
- The documented upstream shared-loader logger and unique-key retention concerns remain; this upgrade does not monkey-patch private upstream internals. Keep debug disabled and qualify long encrypted deployments separately.
- Quality caps are preferences, not security or transfer limits. They can conservatively exclude later acceptable renditions because upstream ladders are not strictly bitrate ordered.
- Offline VOD, DRM adapters, specialised subtitle rendering, persistence/source management, packaged UI and casting remain deferred or application-owned as recorded in the roadmap. OpenTelemetry remains an application bridge.
- No runtime dependency was added. A future minor release is appropriate for the additive API, after qualification and explicit release authorisation.
